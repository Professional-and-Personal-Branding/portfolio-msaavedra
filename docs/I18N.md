# I18N.md — Internacionalización del Portafolio

> Diseño del sistema multi-idioma. **Objetivo central:** un solo conjunto de datos, servido en el idioma demandado en runtime, **sin duplicar registros**. La única variabilidad es el idioma; el contenido es el mismo dato traducido.

---

## 1. Principio de diseño

**Un registro, múltiples idiomas.** Una experiencia laboral (ej. Ensitech) es **una sola fila** en la base. Sus campos de texto traducibles (`summary`, `highlights`, `role`) guardan **todas las traducciones** en una estructura por idioma. Al servir, se resuelve el idioma demandado.

```
❌ MAL (duplicación):
   Experience "Ensitech" (es)
   Experience "Ensitech" (en)   ← fila duplicada, se desincroniza

✅ BIEN (un registro localizable):
   Experience "Ensitech" {
     summary: { es: "...", en: "..." }   ← misma fila, traducciones embebidas
   }
```

---

## 2. Campos traducibles vs. no traducibles

| Traducibles (varían por idioma) | NO traducibles (iguales en todo idioma) |
|---|---|
| `Profile.headline`, `Profile.summary` | nombre, email, teléfono, ubicación |
| `Experience.role`, `summary`, `highlights` | empresa, fechas, tecnologías, tags |
| `SkillCategory.name` | nombres de skills (Java, Docker…) |
| `Education.degree` | institución, fechas |
| `Certification.name` | emisor, año |
| `Project.summary`, `role` | nombre del proyecto, tecnologías, tags |
| `CuratedProfile.title`, `headline`, `description` | slug, filterTags, accentColor |

Regla: nombres propios, tecnologías, fechas y tags **no se traducen**. El texto narrativo y los títulos de rol **sí**.

---

## 3. Modelo de datos: campo JSON localizado

Se introduce un tipo `LocalizedText` = objeto JSON con claves de idioma ISO 639-1:

```jsonc
{ "es": "Texto en español", "en": "English text" }
```

En Prisma, los campos traducibles pasan de `String` a `Json`:

```prisma
model Experience {
  id           String   @id @default(cuid())
  company      String                    // no traducible
  role         Json                      // LocalizedText
  summary      Json                      // LocalizedText
  highlights   Json                      // LocalizedText[] → { es: string[], en: string[] }
  technologies String[]                  // no traducible
  tags         String[]                  // no traducible
  // ...
}
```

> **Por qué JSON y no tabla de traducciones:** para un MVP con un único "dueño" del perfil (Manuel), el overhead de una tabla `translations` con joins no se justifica. El JSON localizado es simple, type-safe con un wrapper, y evita N+1 queries. Si el producto escalara a multi-usuario con muchos idiomas, se migraría a tabla dedicada.

## 4. La función switch de idioma (resolución)

El núcleo puro de i18n (tipos y `resolveLocale`/`resolveLocaleList`) vive en `shared/domain/i18n` para que domain y application lo usen sin violar la regla de dependencia; `shared/infrastructure/i18n/resolve-locale.ts` lo re-exporta (fachada) y agrega `normalizeLocale` / `pickFromAcceptLanguage` (parsing HTTP). Los **mappers de aplicación** (entidad bilingüe → DTO de salida) aplican `resolveLocale` con el idioma demandado y **fallback** al idioma origen:

```typescript
// shared/domain/i18n (núcleo puro; fachada en shared/infrastructure/i18n/resolve-locale.ts)
export type Locale = 'es' | 'en';
export type LocalizedText = Partial<Record<Locale, string>>;
export type LocalizedList = Partial<Record<Locale, string[]>>;

export const DEFAULT_LOCALE: Locale = 'es';   // idioma origen del seed

export function resolveLocale(
  field: LocalizedText | null | undefined,
  locale: Locale,
  fallback: Locale = DEFAULT_LOCALE,
): string {
  if (!field) return '';
  return field[locale] ?? field[fallback] ?? Object.values(field)[0] ?? '';
}

export function resolveLocaleList(
  field: LocalizedList | null | undefined,
  locale: Locale,
  fallback: Locale = DEFAULT_LOCALE,
): string[] {
  if (!field) return [];
  return field[locale] ?? field[fallback] ?? Object.values(field)[0] ?? [];
}
```

**Flujo en runtime:**
1. La request trae el idioma: `GET /api/curated-profiles/java-senior-backend?locale=en`
   (precedencia: `?locale=` > `?lang=` > header `Accept-Language` > `es`).
2. El caso de uso `ResolveCuratedProfileUseCase` recibe `locale: Locale`.
3. El mapper de aplicación (entidad de dominio → DTO) aplica `resolveLocale(exp.summary, locale)` a cada campo traducible. Las entidades de dominio siguen siendo bilingües (necesario para el CRUD de Fase 3).
4. El DTO de salida ya viene "aplanado" en el idioma demandado — el frontend recibe strings simples, no objetos localizados.

> El frontend **no** maneja la lógica de traducción; recibe el contenido ya resuelto. Esto mantiene el frontend simple y la lógica i18n centralizada en el backend.

## 5. Persistencia y no-duplicación

- **Una fila por experiencia/skill/perfil**, sin importar cuántos idiomas tenga.
- Agregar un idioma nuevo = agregar una clave al JSON (`{ es, en, pt }`), **no** una fila nueva.
- El `slug` de un perfil curado es único y **compartido** entre idiomas: `/p/java-senior-backend?lang=es` y `?lang=en` son el **mismo** registro, distinta proyección.
- Las analíticas (`ProfileView`) pueden registrar el `locale` servido para saber en qué idioma se consume cada perfil — sin duplicar el perfil.

## 6. El seed bilingüe

`cv-data.json` se reestructura para que los campos traducibles sean objetos `{ es, en }`. El seed carga **una sola vez** ambos idiomas en cada registro:

```jsonc
{
  "id": "ensitech",
  "company": "Ensitech (Openpay México)",        // plano
  "role": { "es": "Ingeniero de Software Senior", "en": "Senior Software Engineer" },
  "summary": {
    "es": "Desarrollo backend especializado en pagos...",
    "en": "Backend development specialized in payments..."
  },
  "highlights": {
    "es": ["Diseño del microservicio de tokenización...", "..."],
    "en": ["Design of the tokenization microservice...", "..."]
  },
  "technologies": ["Java 17", "Spring Boot 3.x"],  // plano
  "tags": ["java", "spring-boot"]                  // plano
}
```

El seeder detecta si un campo es objeto localizado o string plano (compatibilidad), y lo persiste como JSON. Una utilidad `localize(es, en)` ayuda a construir estos objetos.

---

## 7. Function switch — punto único de cambio de idioma

El "switch de idioma" vive en **un solo lugar** (`resolveLocale`). Cambiar el idioma de toda la respuesta es pasar un parámetro distinto:

```typescript
// Mismo dato, distinta proyección — sin duplicar nada
const profileES = await resolveCuratedProfile.execute({ slug, locale: 'es' });
const profileEN = await resolveCuratedProfile.execute({ slug, locale: 'en' });
```

Para agregar portugués en el futuro: (1) agregar `'pt'` al tipo `Locale`, (2) agregar la clave `pt` a los JSON que se quiera traducir, (3) listo — el fallback cubre lo que falte.

---

## 8. Exportación de CV / PDF por idioma

Cuando se implemente la exportación a PDF (Fase 6), el mismo `locale` alimenta el generador: un único motor de plantilla produce el CV en el idioma demandado, reutilizando exactamente los datos ya traducidos en la base. **Cero CVs duplicados como archivos** — se generan on-demand en el idioma pedido.

---

## 9. Resumen de cambios para Claude Code

1. **Schema:** campos traducibles (`role`, `summary`, `highlights`, `headline`, `title`, `description`, `degree`, `name` de categorías) pasan de `String`/`String[]` a `Json`.
2. **Seed:** `cv-data.json` con campos `{ es, en }`; `seed.ts` con helper `localize()` y persistencia como JSON.
3. **Shared:** núcleo `shared/domain/i18n` con `Locale`, `LocalizedText`, `resolveLocale`, `resolveLocaleList`, `DEFAULT_LOCALE`; fachada `shared/infrastructure/i18n/resolve-locale.ts` con `normalizeLocale`.
4. **Casos de uso:** aceptan `locale: Locale` y lo propagan a los mappers.
5. **Controllers:** leen el idioma con `@RequestLocale()`: query `?locale=`, alias `?lang=`, header `Accept-Language`; default `es`. El locale servido se informa en `Content-Language`.
6. **DTOs de salida:** strings ya resueltos (el frontend no ve objetos localizados).
